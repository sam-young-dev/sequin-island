## Design Specificity Verdict

**LLM assessment (Assessment A):** Mostly generic, with the specificity smuggled in entirely through prose content rather than structure. The `blog` schema has no `author` field — nothing distinguishes "S&S" as a byline. The sign-off "Light and love, / S&S" renders as two more `<p>` tags in `.prose`, styled identically to the paragraph above it. Strip the words "Keeper's Blog" from the h1 and this is any Astro content-collection blog: title, date, excerpt, markdown body, one back-link. DESIGN.md's own "Letter from the Island Rule" is honored as a *typography* rule (Source Serif 4, 1.65 leading, 70ch measure) but never becomes an *authorship* rule — the template stops at the font choice.

**Deterministic scan (Assessment B):** `impeccable detect --json` returned **zero findings** across `src/pages/blog`, `src/pages/index.astro`, and `src/components/card/Card.astro` (exit code 0). A sanity re-scan of the whole `src/` tree confirmed the tool is live (it found 2 unrelated `design-system-radius` advisories in `prose.css`, outside this surface). This is expected: the real issues on this surface are architectural/UX, not mechanically detectable class-name or token violations.

**Browser evidence (Assessment B), and where it overturns the LLM read:** The largest self-correction of this run: Assessment A treated the post body's four `![]()` markdown images (hotlinked to `seguinisland.org/wp-content/uploads/...`) as an unmitigated **P0 reliability risk with no failure design**. Checking [astro.config.mjs](astro.config.mjs) shows this is already deliberately solved — `image: { domains: ["seguinisland.org"] }` authorizes Astro to download and optimize those remote images *at build time*, and Assessment B's DOM inspection of the live page confirmed it: in-body images are served through Astro's `/_image?...&f=webp` pipeline with correct intrinsic dimensions (a 1024×768 source measured 643×482, ratio-correct; a 768×1024 source measured 643×857, ratio-correct). So the in-body images are **not** a live hotlinking risk, and Assessment A's related P3 ("no width/height causes CLS") is also refuted — dimensions are correct and CLS-safe.

The risk Assessment A described *is* real, just in the wrong place: the **homepage's dispatch teaser image is the one image on this surface that genuinely is raw and hotlinked**. Source inspection confirms `src/pages/index.astro`'s teaser renders a bare `<img src={latestPhoto.src}>` pointed straight at the external WordPress URL, bypassing Astro's image pipeline entirely (unlike every in-body image), with hardcoded `width="1024" height="768"` regardless of the source photo's real shape. Assessment B independently confirmed via the DOM that this specific post's real second image (`IMG_2420-768x1024.jpeg`, a portrait crew photo) is exactly the kind of image the regex-based extraction (`/!\[(?<alt>[^\]]*)\]\((?<src>\S+?)\)/`, grabbing whichever image is textually first) would surface here if it happened to lead the post. Today it currently renders fine only because `dispatch.css`'s `aspect-ratio: 4/3; object-fit: cover` crops whatever arrives into a fixed box — no visible stretching, but a portrait "hero" gets cropped into an unrecognizable strip, and there is no design story for that outcome.

## Overall Impression

The blog's prose typography and voice are genuinely well-executed and faithful to the site's own design language. The gap is structural: the template treats "Keeper's Blog" as a generic content-collection blog rather than as the letter-from-real-people the product's own naming and PRODUCT.md promise. The single biggest opportunity is giving the homepage teaser (the site's primary blog entry point, and its highest-traffic exposure) a deliberate, author-chosen hero image instead of parsing prose for one — that single fix also resolves the schema's total blindness to images.

## What's Working

- **Prose typography is disciplined and comfortable.** [prose.css](src/styles/blocks/prose.css) delivers the DESIGN.md-specified 70ch paragraph measure, 65ch article cap, and 1.65 line-height exactly as documented — genuinely the strongest thing on this surface.
- **The content schema is a smart guardrail for volunteer editors.** [content.config.ts](src/content.config.ts)'s placeholder-text regex and per-field length bounds (enforced only when `draft: false`) catch half-finished posts before they ship, without adding friction to drafts.
- **In-body remote images are handled correctly, not naively.** `astro.config.mjs`'s authorized `domains: ["seguinisland.org"]` plus Astro's markdown image pipeline means the WordPress-hosted photos in the one real post are downloaded, optimized to webp, and ship with correct intrinsic dimensions — a deliberate, working solution to a real migration-era problem, confirmed by direct DOM measurement.

## Priority Issues

- **[P0] The homepage's blog teaser hotlinks a raw external image and guesses at a hero it was never told to choose.** `src/pages/index.astro`'s `dispatch` section extracts `latestPhoto` via a regex against the raw markdown body and renders it as a bare `<img src="https://seguinisland.org/...">` with hardcoded `width="1024" height="768"`, bypassing the same Astro image pipeline that correctly protects every in-body image. **Why it matters:** this is the site's primary, highest-visibility entry point into the blog; it depends on the external WordPress host at every runtime page view (not just at build time, unlike in-body images), and it will crop a portrait photo unrecognizably the day a caretaker's first-in-post image isn't a landscape 4:3 shot — which this very post's actual second image proves is a realistic scenario. **Fix:** add an explicit `heroImage` field to the `blog` schema (via Astro's `image()` helper) that a caretaker deliberately sets, and route it through the same optimized `<Image>` pipeline the body already uses instead of regex-scraping prose.
  **Suggested command:** `/impeccable harden`

- **[P1] No byline or signature treatment for the post's own sign-off.** "Light and love, / S&S" — the line that most embodies DESIGN.md's "Letter from the Island Rule" — renders as two more identical `<p>` tags in `.prose`, indistinguishable from any other paragraph. **Why it matters:** the emotional payoff the product's own naming promises (a personal letter from real caretakers) is asserted in the design system but never designed into the actual artifact; a reader gets no closing beat after two minutes with a warm, personal update. **Fix:** give the sign-off a distinct treatment (e.g. an italic or accent-ruled closing block), and/or add an `author` field surfaced near the dateline in `[slug].astro`.
  **Suggested command:** `/impeccable delight`

- **[P1] No `socialImage` is passed from either blog page, even though the plumbing already exists.** `BaseLayout`/`MetaInfo.astro` already support a `socialImage` prop and render `og:image` when given one, but neither `blog/index.astro` nor `blog/[slug].astro` pass it. **Why it matters:** for a volunteer nonprofit whose most likely sharing channel is Facebook/Instagram, a shared post link with no preview image is a real, avoidable cost to reach and donations — and a strong candidate image already exists per post. **Fix:** pass the post's hero image (once it exists per the P0 fix above) as `socialImage` to `BaseLayout` on both pages.
  **Suggested command:** `/impeccable harden`

- **[P2] The blog listing grid leaves ~900px of dead whitespace next to a single card at desktop width.** Confirmed via live browser inspection at 1440px: `blog/index.astro`'s `.grid` relies on `--grid-item-min: 20rem` with `grid.css`'s default `--grid-placement: auto-fill`, which reserves multiple empty tracks instead of letting the one real card fill the row. **Why it matters:** this is the exact state the blog is in *right now* (one published post), so it's a live defect, not a future edge case — and it directly costs the "Aesthetic and Minimalist Design" heuristic a point. **Fix:** switch to `auto-fit` for this grid (or any grid expected to sometimes hold a single item), so empty tracks collapse and the lone card fills available space.
  **Suggested command:** `/impeccable layout`

- **[P2] Empty-state copy diverges between the two places a visitor can see "no posts yet."** `blog/index.astro` reads "Check back soon, or read the island's history," while the homepage dispatch section reads "…explore the island in 3D," for the identical underlying condition, with nothing in either file signaling the divergence is intentional. **Why it matters:** small, but it reads as drift rather than a deliberate voice choice, and it's the kind of inconsistency that compounds as more empty/edge states get added. **Fix:** either unify the copy or add a one-line comment explaining why the two contexts intentionally differ.
  **Suggested command:** `/impeccable clarify`

- **[P3] No way to follow the blog for updates.** No RSS feed, no email/subscribe link anywhere on the surface, despite PRODUCT.md's own "trip planners and returning members" audience wanting exactly these seasonal caretaker updates. **Why it matters:** the persona most motivated to read this blog (a returning member checking for news) currently has to remember to manually revisit `/blog`. **Fix:** ship an Astro RSS feed at minimum; a lightweight "new post" signal elsewhere (email list, etc.) is a larger scope call for the user.
  **Suggested command:** `/impeccable onboard`

## Persona Red Flags

**First-time visitor deciding whether to donate:** Lands on the homepage dispatch teaser expecting a "real place, real people" moment, and instead reads a well-written but structurally anonymous post — no clear "these are the caretakers" framing beyond a two-letter sign-off buried in body text. If the teaser's hotlinked image is ever slow or a future post's lead photo is portrait, the credibility hit lands immediately before the donation ask further down the same page.

**Returning member checking for news:** Has to remember to manually revisit `/blog` — no RSS, no follow mechanism (Help and Documentation heuristic gap) — despite PRODUCT.md explicitly wanting this audience to catch seasonal caretaker updates (tower closures, berry season, visiting schooners).

**Caretaker publishing a post via the CMS:** Drops a phone photo in as their first image without knowing it will silently become the homepage's hardcoded-aspect-ratio hero the moment it publishes — the schema has no field to mark "this is the post's hero image," so their only lever is *where in the markdown body they place images*, an implicit and fragile authoring contract nobody told them about.

## Minor Observations

- Card heading sizing is correctly consistent: the blog index uses `<h2>` under a page `<h1>`, and the homepage's "earlier posts" grid uses `<h3>` under a section `<h2>`, matching DESIGN.md's card-heading-size rule.
- The zod schema's `superRefine` correctly skips its strict length/placeholder checks when `draft: true`, so `_placeholder.md` never trips validation and (correctly) never renders live.
- `dispatch__feature:not([data-has-photo])` already has a graceful no-photo fallback (a ruled border treatment) for the *teaser* when there's no image at all — a good instinct that was never extended to cover a *wrong-shaped* image, which is the more likely failure mode given the regex extraction.
- The mobile header nav wrapping to two/three rows (no hamburger menu) is confirmed intentional per DESIGN.md, not a defect.

## Provocative Questions

1. If this site exists specifically to help FOSILS leave WordPress, why does the homepage's single highest-visibility blog element still depend on WordPress's media library staying online at every page view, when the in-body images already prove the safer pattern exists?
2. The content schema enforces excerpt length, placeholder-text rejection, and description bounds with real rigor — so why does it have zero opinion about the one field (images) most likely to break visually?
3. Is "Keeper's Blog" written by one consistent voice, or does it rotate season to season — and if the latter, doesn't that make an `author` field a near-term necessity rather than a nice-to-have?
